# Components

## Folder anatomy

```
src/components/<Feature>/
  <Feature>.tsx                 container: reads hooks, handles loading/error/empty
  <Feature>.module.css
  <Feature>.test.tsx
  <Feature>Card/
    <Feature>Card.tsx           presentational
    <Feature>Card.types.ts
    <Feature>Card.module.css
  <Feature>Skeleton/
    <Feature>Skeleton.tsx
```

Sub-components of a feature live **inside** the feature folder (`Reports/ReportsCard/`, `Entries/EntriesList/`).

## Component template

```tsx
import { type FooProps } from './Foo.types.ts';
import styles from './Foo.module.css';

export const Foo = ({ title, variant = 'default' }: FooProps) => {
  return (
    <div className={styles.foo} data-testid="foo">
      {title}
    </div>
  );
};
```

```ts
// Foo.types.ts
export interface FooProps {
  title: string;
  variant?: 'default' | 'highlighted';
}
```

Rules:
- Destructure props in the signature; defaults there too.
- Props interfaces live in `<Name>.types.ts` once there's more than a trivial inline type.
- Containers (read context/hooks) vs presentational (props only). Presentational components must not call data hooks.
- Early returns for states: `if (isLoading) return <Skeleton/>; if (error) return <Error/>;`.
- Lists use stable keys (`entry.id`), never array index.

## Compound components

Use for cards with flexible slots (see `EntriesCard`):

```tsx
export const EntriesCard = ({ children, className }: EntriesCardProps) => …;
const Header = ({ children }: EntriesCardHeaderProps) => …;
EntriesCard.Header = Header;
```

Usage reads top-to-bottom: `<EntriesCard><EntriesCard.Header>…</EntriesCard.Header></EntriesCard>`.

## Config maps over conditionals

Map variants with a typed record instead of `if/else` chains:

```ts
const TYPE_CONFIG: Record<string, { icon: IconType; label: string; className: string }> = { … };
const config = TYPE_CONFIG[type] ?? TYPE_CONFIG.DEFAULT;
```

## Forms

- `react-hook-form`; logic in a dedicated hook (`useEntryForm`) that returns `useForm(...)` plus `submitForm`.
- Validation rules, defaults and payload builders in `<Form>.helpers.ts` (`entryFormRules`, `buildEntryPayload`).
- Chakra `Field.Root invalid` + `Field.ErrorText`; Chakra `Select` via `Controller`.
- Dialog forms use `FormDialog` from `components/ui/form-dialog.tsx` with `submitFormId` linking the submit button to `<form id>`.

## Dialogs

Reuse `ConfirmDialog` (destructive confirmations) and `FormDialog` (forms). Control with `open` + `onOpenChange={(d) => { if (!d.open) close(); }}`.

## Accessibility

- Icon-only buttons need `aria-label` with context: `aria-label={\`Delete flight from ${date}\`}`.
- Decorative separators: `aria-hidden="true"`.
- Use semantic elements (`nav`, `main`, `h2`, `button`) — don't put `onClick` on `div`s.
- Prefer queries by role/label in tests; this enforces accessible markup.

## Skeletons

Every async container ships a skeleton that reuses the real component's CSS module classes (see `EntriesCardSkeleton` importing `EntriesCard.module.css`) so layout doesn't shift.

## Chakra UI snippets (`components/ui`)

Generated by the Chakra CLI; they use `forwardRef`, `function` declarations and `'use client'`. Leave their style as is; extend via props (`contentProps`, `backdropProps`, …) rather than forking.
